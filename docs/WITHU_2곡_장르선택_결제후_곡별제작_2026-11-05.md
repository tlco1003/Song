# WITHU — 2곡 상품 사용자 장르 선택과 결제 후 곡별 제작 규칙

작성일 2026-11-05 · 현재 상태: 설계·검증 완료, 결제 및 Suno 상업 API 미활성화.

## 사용자 선택 동작

- `audio`(29,000원): 가사 작성 화면의 `genre`를 주문 화면에서 다시 변경 가능. 정확히 1개 장르.
- `audio_duo`(39,000원): **두 가지 선택지를 모두 제공**.
  1. `mode=same`, `genres=['발라드']` ⇒ 같은 가사로 발라드 1곡과 **새롭게 생성한** 발라드 2곡. 같은 MP3를 두 번 제공하지 않음. 2번째 멜로디·편곡은 독립 요청.
  2. `mode=different`, `genres=['발라드','재즈']` ⇒ 같은 가사로 발라드 한 곡, 재즈 한 곡.
  3. 다른 장르 방식에서 `['발라드','발라드']` 중복 선택은 잘못된 입력. 고객은 '한 장르로 2곡' 모드를 선택하도록 안내.
- `audio_video`(300,000원부터, 사전 견적): 한 장르 1곡 + 영상 제작 범위 협의. 이번 2곡 기능 변경으로 기존 영상 고객 입력을 바꾸지 않음.
- 장르 선택지는 `docs/music-genres.json`의 7가지. 작사 화면 선택을 초기값으로 사용하되 주문 화면에서 변경할 수 있음.
- 주문 화면을 다시 열어도 상품·모드·첫/둘째 장르·공통 음악 요청사항을 현재 브라우저의 단기 `sessionStorage` 초안에서 복구. 별도 URL에 개인정보가 실리지 않음.
- 고객이 `create.html`에서 작성한 음악 스타일이 자동 채움값이 아니라 직접 수정한 내용이라면 500자까지 '공통 음악 요청사항'에 가져와 고객이 확인/수정 가능. 원래 선택된 첫 장르용 **자동 프롬프트**를 다른 장르에 그대로 붙이지 않음.

## 입력 계약: 고객 초안에서 서버 주문까지

```json
{
  "productId": "audio_duo",
  "songTitle": "엄마에게",
  "confirmedLyrics": "엄마, 고마워요...",
  "mood": "따뜻한",
  "genreSelection": {
    "mode": "different",
    "genres": ["발라드", "재즈"]
  },
  "sharedStyleNotes": "맑은 여성 보컬, 시작은 조용하게"
}
```

`genreSelection`은 단지 고객이 원하는 내용. 실결제 개발 시 주문 생성 API가 이를 **서버에서** `normalizeGenreSelection()`로 검증하고 고객 승인 결과를 영속 DB에 저장해야 한다. 현재 공개 `/api/commerce/orders`는 503으로 계속 차단되어 있고 **실제 주문 데이터가 서버에 들어오지 않는다**.

## 결제 후 공통 게이트

```text
선택 저장(결제 전) → 서버 주문에 스냅샷 기록 → 결제 인증
→ PG에서 DONE 및 주문번호·원 금액 확인 → 주문 상태 PAID
→ 한 트랜잭션에서 paidSongPlan + fulfillment outbox 원자적 생성
→ 서버가 승인된 처리 경로 하나를 선택
  ├─ manual_operator: 운영자 메일에 '1곡 발라드 / 2곡 재즈'와 곡별 스타일 프롬프트
  └─ approved_music_api: 곡별 2개의 독립 음악 생성 요청
        withu-music-{orderId}-1
        withu-music-{orderId}-2
```

- 위 흐름은 `src/song-production-plan.mjs`, `src/paid-order-pipeline.mjs`, `src/operator-notification.mjs`로 이어진다.
- `src/song-production-plan.mjs`은 승인된 7개 장르와 분위기, 고객이 선택한 공통 음악 지시사항을 사용해 **곡별로 다른** `stylePrompt`를 생성한다.
- 두 번째 곡이 첫 번째와 같은 장르여도 두 번째는 별도 `song.index=2`, 별도 프롬프트와 중복 방지 키가 할당된다.
- 수동 이메일은 최종 `paidSongPlan`에 기록된 곡 수, 각 장르, 스타일을 정확히 명시한다.
- `verifyPaidSongPlan()`은 결제 확정 당시 저장한 장르 스냅샷과 작업 실행 직전 주문 데이터가 일치하는지 검사한다.
- API가 승인이 나기 전에는 실 Suno 호출을 하지 않는다. 승인이 나더라도 라이선스 범위·API 스키마·결제사·보안 주문저장소·멱등성 있는 재시도 큐를 먼저 완성해야 한다.
- 이미 결제가 된 주문의 장르 변경은 원 결제 작업에 덮어쓰지 말고 고객 승인/운영자 권한 있는 **주문 수정 버전**과 재검증 절차로 처리.

## 남은 상용화 필수 작업

PG 상점 계약, 영속 주문 DB/트랜잭션 Outbox 구현, 실 Resend 이메일 발신인 검증과 환경변수 주입, 고객 이메일 전송/파일 보호, Suno의 서면 수동 납품 및 사업용 API 계약, 환불 및 개인정보 고지 등이 먼저 필요하다. 이 문서와 코드가 **실결제 가능이나 Suno 승인**을 뜻하지 않는다.
