# WITHU — 결제 검증 후에만 실행되는 수동·자동 제작 2갈래 파이프라인

작성: 2026-11-05
저장소: `tlco1003/Song` · 브랜치 `main`
**현재 상태: 구현 계약 및 테스트 가능한 어댑터 준비. 실결제·주문 접수·운영자 이메일 발송·Suno API 자동생성은 모두 비활성.**

## 목표

공통 주문 과정은 한 가지이며 **PG 승인·입금 완료 이후에만** 제작 작업을 발행한다.

```text
고객 사연 입력 → 가사·스타일 최종 확정 → 상품·배송 이메일·약관 확인
             ↓
     운영 서버가 주문 ID + 서버 소유 가격을 DB에 영속 저장
             ↓
        공식 PG 결제 인증창 / 가상계좌 발급
             ↓
  백엔드에서 PG 승인 API 또는 검증된 입금 이벤트 + 결제 재조회
             ↓
            status == DONE ?
          ├── NO → 주문 보류 (알림/제작 없음)
          └── YES → 금액·주문번호·결제키·통화 검증
                    ↓
          DB 트랜잭션으로 PAID + 출고 outbox 1건 기록
                    ↓
             [서버가 운영 방식을 결정]
             ├── 수동 제작 (기본, API 승인 전)
             │   └── Resend로 운영자에게 유료 주문서 메일
             │       → 사람이 Suno에서 적법한 계약 범위로 제작
             │       → 최종 파일 검수 및 안전한 고객 이메일 전송
             └── 승인된 Suno B2B API 자동 제작 (추후)
                 └── 허가된 API 생성 작업 → 결과 검증·저장
                     → 고객에게 비공개 다운로드 링크 이메일 전송
```

**금지:** 고객 폼 제출, 리다이렉트 성공 쿼리, 계좌 발급 응답, 브라우저의 `paid:true`, 수기 계좌입금 사진, 임의 코드의 환경변수 하나로 출고 또는 이메일을 발송하면 안 된다.

API 승인 전 기본 모드는 `manual_operator`이다. `approved_music_api` 모드는 서버의 **`preference=approved_music_api` + `commercialApiAgreementVerified=true` + `musicProviderReady=true`** 조건을 모두 만족해야만 선택된다. 실제 상업용 음악 어댑터 스키마와 인증·범위는 **계약 후 공식 문서로 구현**한다. 고객 입력이 작업 모드를 바꾸지 않는다.

## 실제 운영 전 반드시 추가 구현할 구성 요소

1. **영속 주문 DB**: 예를 들어 운영 PostgreSQL. 주문번호·상품·서버에서 고정한 금액·최종 가사 버전·암호화한 수신 이메일·결제 상태·고객 동의 기록을 저장한다. 결제 후 리다이렉트만 보고 메모리에서 생성한 주문은 인정하지 않는다.
2. **원자적 결제+작업 대기열**: `orders.confirmPaidAndEnqueueAtomic()` 포트를 PostgreSQL 트랜잭션으로 구현. 주문당 작업 `fulfill:{orderId}`에 유니크 제약을 걸어 **동시 콜백/재시도에도 한 번만** 생성한다. 작업 실행 성공/실패/재시도·lease 상태를 DB에 기록한다.
3. **실결제 PG 가맹점 키/계약**: `TOSS_SECRET_KEY`와 공개 클라이언트 키를 다른 영역에서 관리. 브라우저에서 받은 결제 정보를 서버 주문과 대조하고 PG confirm API를 실행한다. 주문 생성 및 승인 API 엔드포인트는 아직 구현되지 않았다. 기존 `/api/commerce/orders`는 계속 503.
4. **가상계좌**: `WAITING_FOR_DEPOSIT`이면 출고 금지. PG `DEPOSIT_CALLBACK` 이벤트를 인증하고 공식 API로 상태를 재조회하여 `DONE`이면 동일한 트랜잭션 흐름으로 전환. 가상계좌의 최초 secret, 주문별 paymentKey를 DB에 보안 저장.
5. **운영자 이메일**: Resend 도메인과 발송인 인증 후 `RESEND_API_KEY`, `WITHU_FROM_EMAIL`, `WITHU_OPERATOR_EMAIL`을 비밀 서버 설정에 입력. 고객 사연·가사·이메일은 결제 검증 후에만 운영자에게 메일 본문으로 전달. 얼굴/목소리 원본은 이메일에 첨부하지 않는다. `Idempotency-Key: withu-operator-{orderId}`로 발송 중복 최소화. 이메일 전송 전 개인정보 처리 고지·법적 근거·관리자 보안을 확정.
6. **운영자 작업 페이지**: 결제 확인된 주문만 인증된 관리자에게 보여주고, 직접 완성곡을 올리고, 검수 후 고객에게 보내는 절차. 제작중·완료·환불·전달 실패 상태 변경은 권한 있는 서버에서만 수행.
7. **고객 배송 메일**: 비공개 저장소(S3/R2 등)에 생성물 보관, 서명된 만료형 링크 사용, Resend에서 고객에게 발송. 결제 확인 메일·제작 완료 메일·운영자 알림 메일은 서로 다르다.
8. **Suno 수동 제작권**: 정식 B2B API 허가 전이라도 직접 Suno로 고객용 유료 맞춤 음악을 제작·납품할 수 있는지 **Suno의 명시적 서면 확인 필요**. API 없는 수작업이라는 이유로 재판매 권한이 자동 부여되는 것은 아니다.
9. **운영 안전성**: 불특정 고객 대상 인증·속도 제한·개인정보 암호화·관리자 권한·취소/환불·오발송 방지·감사 로그·보안성 테스트·실제 소액 샌드박스 거래 검증.

## 개발자가 구현할 함수 계약

- `confirmCheckoutAndQueue({orderId,paymentKey,claimedAmountKrw,orders,payments,settings})`: PG 서버 승인 결과가 `DONE`이며 서버 주문의 ID/키/원 단위 가격과 일치할 때만 `confirmPaidAndEnqueueAtomic()` 호출. 승인 전 직접 메일 발송하지 않음.
- `reconcileDepositAndQueue({orderId,paymentKey,orders,payments,settings})`: 발급된 가상계좌의 입금 이벤트를 **인증한 뒤** 실제 PG 상태를 다시 조회하고 `DONE` 확인 시만 outbox 큐에 추가.
- `chooseFulfillmentRoute(settings)`: 기본 `manual_operator`; 공식 Suno B2B 승인 및 어댑터 검증 후 `approved_music_api`.
- `executePaidJob({job,order,operatorEmail,musicProvider})`: `PAID`, `paymentVerifiedAt`, `paymentKey`, `claimed` 잡 증빙이 있는 경우에만 운영자 이메일 또는 승인된 API 생성 진입.
- `makeResendOperatorEmail()` 및 `makeTossPaymentAdapter()`는 비공개 Node 서버에서만 실행. 구체적인 외부 업체 키는 GitHub 커밋에 남기면 안 된다.

**중요:** 이 구현은 안전하게 미리 만든 파이프라인 핵심과 어댑터 및 테스트이지 **운영 결제 연결이 끝났다는 뜻은 아니다**. 운영 DB, 안전한 HTTP 결제 라우트, PG 상점 인증, Resend 메일 설정, 적법한 음악 라이선스가 모두 준비되기 전에는 실제 유료 주문을 열지 않는다.
