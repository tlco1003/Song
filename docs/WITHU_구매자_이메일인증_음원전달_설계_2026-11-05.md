# WITHU — 결제 이메일 인증 기반 개인 음악 선물함

작성: 2026-11-05
대상 저장소: `tlco1003/Song`
구현 브랜치: `feature/customer-only-delivery-20261105`

## 고객이 보는 실제 화면 구조

### 홈 / 공개 감상 (`docs/index.html`)

- 방문자는 운영자가 공개를 허락한 예시 음원을 들을 수 있다.
- 곡 제목 → 장르·분위기·설명 → **가사(세 줄 뷰)** → 플레이어 순서로 표시한다.
- 공개 홈 가사 복사 버튼과 관련 클립보드 코드가 없다. 단, 화면에 보이는 가사를 개발자 도구나 수동 입력 등으로 완전히 복제 방지할 수는 없다.
- 이전 `song.html?demo=song-...` 주소는 생성하지 않는다.
- 공개 홈의 `내 노래 확인하기` / `내 노래`는 **고객 선물함 `song.html`** 으로만 이동한다. 홈의 음악 ID는 개인 주문 열람 권한이 아니다.
- `docs/media/`에 있는 MP3/MP4와 가사는 **공개 샘플**이다. 여기에 개인 구매 파일을 올리면 GitHub Pages에서 누구나 다운로드할 수 있으므로 반드시 금지한다.

### 결제 후 고객 선물함 (`docs/song.html`)

- 시작 화면: 결제에 사용한 이메일을 입력하여 6자리 인증번호 요청.
- 서버는 결제사 확인을 통과한 영속 주문 데이터의 `customerEmail`에만 인증번호를 발송한다. 존재하지 않는 이메일도 **동일한 공개 응답**을 반환하여 고객 이메일 목록을 유추하지 못하게 한다.
- 10분 내 정확한 코드를 인증하고, 서버의 HttpOnly + Secure + SameSite=Lax 세션 쿠키를 발급받은 뒤에만 본인 구매 내역을 표시한다.
- 제작 진행 중인 주문은 '진행 중'이며 노래 파일은 표시하지 않는다.
- `DELIVERED` 상태의 주문별 최종 검수된 구매곡만 목록에 나타나고, 선택한 곡에 대해 재생·원본 파일 다운로드를 제공한다.
- 구매한 곡이 1곡이면 1개, 2곡이면 최종 선택한 2개만 제공한다. Suno가 내부적으로 여러 후보를 생성했더라도 미선택 후보는 제외한다.
- 뮤직비디오인 경우에는 영상 플레이어를, 음원 상품은 오디오 플레이어를 사용한다.
- 이 화면에 `?demo=`, `#delivery=토큰`, URL의 주문 ID/메일을 넣어도 **인증을 우회할 수 없다**.

## 검증된 결제 후 이메일 흐름

```text
고객 주문서에서 이메일 2회 확인 (프런트 표시용)
→ 서버 영속 주문 생성 (서버 확정 상품·금액·고객 이메일)
→ Toss PG 승인 / 가상계좌 DONE 재검증 (서버만 신뢰)
→ 결제키·서버 확정금액·통화·주문번호 일치 확인
→ 트랜잭션: PAID + 제작 작업 1건 + 구매확인 메일 작업 1건 (각각 고유 키)
→ 메일 워커가 DB의 PG-검증 주문을 확인한 후 구매자에게 결제 확인 메일 발송
→ 운영자 수동 제작 또는 승인된 Suno B2B 제작
→ 운영자/검수 파이프라인에서 구매곡 수대로 최종본 1개씩 선택
→ 비공개 저장소 업로드 및 소유권 매핑 원자적 기록
→ Resend를 통해 결제 이메일로 '완성된 나의 음악 선물함' 알림
   https://실제-도메인/song.html (주문/음원 토큰 없음)
→ 메일 발송사 수락 확인 후 DB 트랜잭션으로 주문 상태 DELIVERED 확정
→ 고객이 결제 이메일로 인증번호 요청
→ 메일에서 6자리 코드 확인, 10분 내 인증
→ 세션 확인과 PG-검증 주문의 소유권 검사
→ 주문에 속한 최종 음원만 임시 전용 URL로 재생/다운로드
```

결제 확인 메일은 `withu-receipt-{orderId}`, 완성 알림은 `withu-delivery-{orderId}`라는 중복 발송 방지 키를 사용하고, 메시지 본문에는 **비공개 파일 경로, 토큰, 결제키, 다른 후보 파일, 고객 사연 전체를 넣지 않는다**. 인증번호는 인증 요청에만 발송한다.

## API 설계 (Node HTTPS 서버)

| 엔드포인트 | 검증 / 동작 |
|---|---|
| `POST /api/delivery/access/request` | 이메일형식 검사, DB에 존재하는 구매자에게만 일회용 코드, 주소/IP 제한 |
| `POST /api/delivery/access/verify` | 10분 TTL, 시도 최대 5회, 일회성 코드 원자적 소비, HttpOnly 세션 발급 |
| `GET /api/delivery/session` | 서버 저장 세션과 만료 확인, 인증된 사용자 이메일 반환 |
| `POST /api/delivery/logout` | 세션 폐기, 만료된 쿠키 응답 |
| `GET /api/delivery/orders` | 인증된 이메일 소유의 PG 완료·미환불 주문만 |
| `GET /api/delivery/orders/:orderId/tracks/:index` | 본인 주문 + DELIVERED + 선택된 파일 1개만 |
| `GET /api/delivery-assets/:opaqueTicket` | 인증 쿠키/만료/주문 소유권/선택된 원본 일치 재검사 뒤 비공개 저장소 스트리밍 |

서버는 이메일 하나만 알면 주문을 확인하게 하지 않으며, **세션 인증과 주문 소유권을 매 요청 확인**한다.

- `src/customer-portal.mjs`: OTP·세션·소유권·개별 파일 요청의 검증 핵심 (기본 어댑터 주입식).
- `src/customer-notification.mjs`: Resend 결제 확인·OTP·완료 알림의 서버 전용 발송 계약.
- `src/customer-payment-receipt.mjs`: PG 승인 상태를 재검사하는 결제 확인 메일 워커 계약.
- `src/customer-delivery.mjs`: 승인된 곡만 영속 기록 후 완성 알림 발송 및 발송 확인 뒤 DELIVERED 상태 확정.
- `src/server.mjs`: 위 전용 경로를 인스턴스화된 `customerPortal`이 **있을 때만** 서비스. 없으면 503.
- `test/customer-portal.test.mjs` 및 `test/song-delivery-selection.test.mjs`: OTP 만료, 타인 주문 접근 거절, 미결제 거부, 1곡/2곡 선별, 노출 금지 테스트.

## 출시 전 꼭 필요한 연결 작업 (아직 미완성)

1. **DB (필수)**: PostgreSQL 등에서 주문·결제 상태·이메일·기록·취소/환불·검수된 곡 정보를 영속 저장. `orders.listByEmail/getById` 실구현.
2. **OTP/세션 저장**: `challenges.issueAtomic/consumeAtomic`는 해시 저장·최대 5회·10분 만료·원자적 일회성 사용을 DB 트랜잭션으로 구현. `rateLimiter.hit`는 이메일/IP 별 독립 한도를 강제, `sessions.create/retrieve/revoke`는 세션 토큰 SHA-256 해시만 저장.
3. **PG 실승인/웹훅**: `TOSS_SECRET_KEY` 서버 비밀 설정, 주문 금액·결제키 비교, 가상계좌 입금 완료 재검증, 중복 승인 차단. 브라우저 `paid=true` 사용 금지.
4. **프라이빗 저장소**: Firebase Storage/Cloud Storage/S3/R2 등 공개가 아닌 객체 저장소. `assets.issueRoutes/resolveTicket/streamAuthorized`를 서버에서 구현. 티켓은 최대 5분, 파일은 GET/HEAD 및 Range(206) 지원, 매 접근마다 세션·소유권 재검증. 소유권 확인되지 않은 URL을 응답하지 않는다.
5. **관리자 검수**: 운영자가 본인 인증 후 최종 파일 업로드하고 품질·저작권·상품 수량을 검증한 다음 상태를 DELIVERED로 변경. 재전송·환불·접근 취소 등 지원.
6. **이메일 서비스**: Resend 도메인 인증·`RESEND_API_KEY`·`WITHU_FROM_EMAIL`·`WITHU_CUSTOMER_PORTAL_URL` (정확한 HTTPS `/song.html`) 입력. OTP·완성 알림은 서버 작업으로만 실행하고 과금이나 작업 실패와 구분 기록.
7. **보안 배포**: 정적 GitHub Pages에 백엔드는 없으므로 같은 도메인 Node/Firebase 인증 경로를 구성해야 한다. `WITHU_CUSTOMER_SESSION_SECRET`는 32바이트 이상 서버 전용 비밀키로 설정. XSS/CSRF 보호, 반송·속도제한, 발송 재시도, 개인정보 보존기간/접근 감사 필요.
8. **적법한 음악 제작권**: Suno와 소비자 맞춤곡 사업자 상업 이용 계약·규격을 확인한 뒤 자동 제작 활성화.

**현재 출고 상태는 의도적으로 CLOSED**: `GET /api/commerce/readiness`는 `canCharge:false`, `POST /api/commerce/orders`는 503이다. 엔드포인트·UI·도메인 계층만 추가했다고 실제 결제, 인증 메일 발송, 개인 음원 다운로드가 운영 가능해지는 것이 아니다. 본 문서의 완료 조건은 실제 서버 연결 및 통합/관통 보안 테스트 후에만 달성한다.

## 개인정보·공개 예시의 경계

- `docs/media`의 예시곡/공개 가사는 공개 리소스로 계속 재생할 수 있다. 실제 고객 파일은 GitHub에 커밋하지 않는다.
- '가사 복사' 버튼 제거는 UX 수정이지 웹페이지에 공개되는 텍스트의 복제 방지 보증이 아니다. 공개하면 안 되는 고객 가사는 아예 공개 화면의 DOM/JSON에 보내지 않는다.
- 서비스 메일 수신 이메일은 **실제 결제 단계에서 서버가 받은 값**으로 고정하며, 주문 후 별도 요청에서 임의로 다른 이메일로 덮어쓰지 않는다.
- 이메일에 담긴 인증코드나 로그인 세션을 URL 쿼리·프래그먼트·localStorage에 넣지 않는다.
