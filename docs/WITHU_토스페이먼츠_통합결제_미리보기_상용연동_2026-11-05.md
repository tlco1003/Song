# WITHU 결제수단 선택 UI 및 상용 결제 연결 계획

작성일: 2026-11-05
저장소: tlco1003/Song (main)

> 현재 상태: **UI 미리보기만 가능하며 실결제·주문 확정·자동 이메일 발송은 불가**. 전시용 상품 가격은 결정되었지만 실거래 상점 계약과 개별 뮤직비디오 최종 견적은 확정되지 않았고, 상업용 음악 생성 API·결제 계약·영속 주문 저장소·이메일 발신 도메인 검증도 아직 완료되지 않았기 때문에 결제 버튼은 fail-closed로 비활성화돼 있다. 사용자의 테스트 선택으로 실제 청구가 발생하지 않는다.

## 현재 구현

- 고객 화면: `docs/checkout.html`, `docs/checkout.css`, `docs/checkout.js`.
- 연결: `create.html`에서 확정한 제목/가사/스타일을 **현재 브라우저의 sessionStorage(30분)**로만 넘긴다. 아직 고객 이메일은 서버에 저장하거나 제출하지 않는다.
- 상품별 전시 예정 가격의 원본은 `docs/prices.json` (노래 1곡 29,000원, **같은 사연·가사 기반의 서로 다른 스타일 2곡** 39,000원, 1곡+뮤직비디오 **300,000원부터**). 뮤직비디오는 `quoteRequired:true`이며 고객이 구체적 범위에 동의한 개별 견적 없이 결제할 수 없다.
- 공개 `GET /prices.json`과 `GET /api/commerce/catalog`은 같은 가격표를 반환한다. 전시 가격은 실제 결제 승인 근거가 아니다. 결제 액면가는 운영 서버에서 주문 시 고정한다.
- 결제수단 미리보기: `toss_pay`, `kakao_pay`, `naver_pay`, `card`, `transfer`, `virtual_account`. 모두 화면만 선택 가능하며 실제 PG SDK 호출은 없다.
- 미리보기 버튼: 결제수단별 설명과 상품 요약만 표시한다. 카드번호/유효기간/CVV/계좌 비밀번호를 사이트 자체에서 입력받지 않는다.
- 실제 결제 버튼은 disabled 유지. 서버의 `/api/commerce/orders`는 의도적으로 503을 반환한다.
- 서버 원칙: `src/commerce.mjs`에서 `canCharge:false` 및 각 도입 검증 값 false. 프런트엔드만 수정해 우회할 수 없어야 한다.

## 추천 PG: 토스페이먼츠 주문서형/결제창형 v2

결제사가 허용한 가맹점 계약 및 수단 활성화 후 **한 번의 PG SDK 연동**으로 카드·토스페이·카카오페이·네이버페이·실시간 계좌이체·가상계좌를 노출하는 방식을 우선 검토한다.

- 최신 공식 개요: https://docs.tosspayments.com/guides/v2/payment-widget
- 결제수단별 정책: https://docs.tosspayments.com/guides/v2/get-started/payment-methods
- 가입/심사: https://docs.tosspayments.com/guides/v2/get-started/payment-products
- 결제 결과 및 이메일 안내: https://docs.tosspayments.com/guides/v2/learn/payment-results
- 가상계좌: https://docs.tosspayments.com/resources/glossary/virtual-account
- 개발 환경과 키: https://docs.tosspayments.com/guides/v2/get-started/environment

**카카오톡** 자체는 결제사가 아니라 메신저 서비스이며, 고객의 결제수단은 **카카오페이**로 구분한다.

## 일반 무통장입금과 가상계좌의 차이

- 일반 계좌번호 공개 후 고객이 송금: 사람이 입금 내역을 확인하거나 별도의 은행 거래내역 조회/대조 시스템을 구축해야 하므로 단순 주문 웹사이트만으로 자동 확인이 되지 않는다. 입금했다고 주장하는 화면·문자만으로 제작을 시작하면 안 된다.
- PG 가상계좌: 주문마다 PG가 계좌를 발급하고 입금 상태 변경을 통지한다. **계좌 발급은 결제 완료가 아니다.** 입금 웹훅 수신 후 서버에서 주문 ID·금액·입금 상태·중복 이벤트를 대조한 다음 제작 큐에 넣는다.
- 카드·간편결제·실시간 이체: 고객 인증 화면으로부터 돌아온 URL의 파라미터만 신뢰하지 않고, **서버에서 결제사 API로 승인** 및 금액 검증 이후에만 주문을 `PAID`로 변경한다.

## 실제 상용 전환을 위한 실행 순서

1. 사업자·통신판매·이용약관·개인정보처리방침·고객 지원/환불 조건을 준비하고 PG의 업종 및 AI 생성 음악 상품에 대한 심사를 받는다.
2. 현재 가격표와 별개로 PG 연동 전에 **서버 소유 주문 시점의 확정 금액** 및 산출물·제작기간·환불 조건을 합의한다. 영상 제작은 300,000원 시작가이며 전체 노래 길이·샷·수정횟수·화면비·얼굴 사용 권한을 확정한 견적 이후에만 구매할 수 있다. 브라우저가 보낸 가격을 승인 기준으로 쓰지 않는다.
3. 테스트 클라이언트 키와 시크릿 키를 구분한다. **서버 시크릿은 GitHub/브라우저/정적 Pages에 넣지 않는다.** SDK v2 사양에 맞춰 PG가 제공하는 UI를 렌더링한다.
4. HTTPS 백엔드, 운영 DB에 `orderId`·상품·가격·확정 가사 버전·수신 이메일(최소 보관/암호화)을 결제 전 저장한다. 주문 ID는 고유하고 재시도에 안전해야 한다.
5. 서버에서 PG 인증 결과와 주문 금액을 대조해 승인하며 중복 요청에 같은 결과를 돌려준다. 토스 웹훅 원문/인증/재조회와 재생 공격, 중복·역순 알림을 다룬다.
6. 가상계좌는 **입금 완료** 확인 전 제작 금지. 카드/간편결제는 PG 확인된 승인 전 제작 금지.
7. 서면으로 허용된 상용 B2B 음악 생성 API, 필요 시 영상 API의 권리·비용·지연·환불 절차를 별도로 완성한다.
8. 상태 기반 영속 작업 큐에서 유료 주문을 **정확히 한 번 제작 등록**한다. 실패 시 재시도, 환불 또는 고객 통지 처리를 제공한다.
9. 완료된 MP3/TXT/MP4는 고객별 비공개 저장소로 보관하고, 인증된 메일 발송 API로 **만료형 다운로드 링크**를 전송한다. PG에서 보내는 **결제 영수증 이메일**은 상품 배송 이메일이 아니다.
10. 성공/실패/취소/환불/중복 웹훅/액면가 위조/가상계좌 미입금/시간초과 등 테스트를 모두 통과한 후에만 라이브 결제를 승인한다.

## 단일결제와 정기 자동결제 구분

고객이 한 번 음악을 구매할 때 결제 결과가 자동 확인되는 것은 **1회성 일반 결제**다. 사용자의 카드를 저장하고 반복 청구하는 **빌링/정기결제**는 별도의 상품·동의·계약과 심사가 필요하다. WITHU의 선물곡 주문에는 기본적으로 빌링을 요구하지 않는다.

## 앞으로 수정할 구조

- UI: `docs/checkout.*` 미리보기 => 계약 후 승인된 결제사 SDK 컨테이너와 주문 확인으로 변경.
- 백엔드: `src/commerce.mjs` 주문 상태 계약 유지, 영속 DB 및 server-side 승인 로직 추가.
- 결제 웹훅: 인증·서명·멱등성·재조회 처리. 상태 오염이나 중복 제작 방지.
- 이메일: 결제 영수증과 제작 완료 산출물 통지를 구분. 실결제 여부와 무관하게 미리보기에서 메일 발송 금지.
- 자동 테스트: `test/commerce.test.mjs`, `test/http.test.mjs`에 부정 경로 및 성공 경로 추가.

이 계획은 **계약이나 라이브 결제 연결이 이루어졌다는 주장이 아니다.**
